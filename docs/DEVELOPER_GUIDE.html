How Shei Hoise is built, shipped, and moved

A working reference for the development team: what the platform does, how the containerized system fits together, how a deploy actually happens, and — because it will come up again — exactly how to move all of this to a fresh VPS without losing a row of data.

What Shei Hoise is

Shei Hoise is a multi-tenant e-commerce platform built for f-commerce sellers — merchants who sell primarily through Facebook and Instagram — as well as standalone online stores. Each store is a fully isolated tenant with its own storefront, products, orders, customers, courier connections, and marketing configuration, all served from one Next.js codebase and one Postgres database using row-level security for tenant isolation.

Meta Pixel & Conversions API

F-commerce sellers acquire nearly all of their customers through Facebook and Instagram ads. Without accurate pixel data, ad platforms can't learn who converts, which drives up customer acquisition cost. Shei Hoise builds Meta Pixel tracking directly into the platform so every merchant gets ad-optimization data without touching any code.

  • Per-store configuration — each store has its own Facebook Pixel ID and, optionally, an encrypted Conversions API access token, set by the merchant in StoreSettingsCard and stored on that store's settings row. The pixel script mounts per-store in the storefront layout — no tenant ever shares another's pixel.
  • Client-side (fbq) — the standard Meta Pixel snippet fires PageView on every route change, capturing UTM parameters and Facebook's fbclid for attribution.
  • Events tracked — PageView, ViewContent, AddToCart, InitiateCheckout, AddPaymentInfo, Purchase, Search — exactly the set Meta's algorithms use to optimize campaigns.
  • Server-side CAPI — matching events are also sent directly to Meta's Graph API, with phone/email hashed (SHA-256) first. This matters because iOS/browser tracking prevention silently drops a large share of browser-only events; sending the same event from both sides (deduplicated via a shared eventID) gives Meta a far more complete signal. CAPI is gated by subscription plan (hasFeature(subscription, "conversion_api")) and only activates once a store has both a Pixel ID and an encrypted CAPI token on file.
  • Merchant-facing analytics — the pixel-analytics dashboard page lets merchants verify their own pixel is firing without needing Meta's Events Manager.

Pathao courier integration

Pathao is one of Bangladesh's largest courier services, integrated alongside Steadfast and manual handling so merchants can fulfill orders without leaving the dashboard.

  • Connection — merchants connect their Pathao account via OAuth from /dashboard/courier/pathao; tokens refresh automatically, credentials are stored per store.
  • Location cascade — City → Zone → Area lookups from Pathao's API, required for Pathao's delivery routing.
  • Shipment creation — converts a Shei Hoise order into a Pathao consignment, recording the consignment ID, delivery fee, COD amount, and weight against the order.
  • Status tracking — refreshable on demand, plus a signed webhook (one callback URL per connected merchant) that updates delivery status and reconciles COD settlement automatically.
  • Unified hub — Pathao, Steadfast, and manual couriers sit in one "Manage Couriers" screen with consistent status displays.

Most Bangladeshi f-commerce sellers rely on COD and third-party dispatch rather than self-delivery — automating shipment creation, tracking, and COD reconciliation removes a large share of manual, error-prone per-order admin work.

Architecture

Nothing about the application code changed when the project containerized. What changed is how the backend is hosted: instead of Vercel-hosted Next.js talking to Supabase Cloud, everything — the app and its own self-hosted copy of Supabase — runs as Docker containers wired through a single gateway. The same containers run on the production VPS.

How a request actually flows

  1. A merchant opens the dashboard, or a customer opens a storefront — hits app.
  2. The app's Supabase client (browser or server) calls Kong.
  3. Kong authenticates the request (API key / JWT) and forwards it to auth, rest, or storage over the internal Docker network.
  4. That service talks to db to do the actual work, enforcing RLS the whole way.
  5. For file uploads/downloads, storage additionally talks to R2 (or MinIO) to store/retrieve bytes; Postgres only tracks bucket/object metadata.
  6. The response returns through Kong to the app — identical to how it worked against Supabase Cloud.
The one real gotcha — build-time vs runtime config

Next.js bakes every NEXT_PUBLIC_* variable into the compiled JavaScript at docker build time, not at container startup. NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY, and NEXT_PUBLIC_SITE_URL are passed as Docker build arguments, sourced from the active env file. UPSTASH_REDIS_REST_URL/TOKEN also had to become build args, because src/lib/redis/redis.ts constructs its client the moment the module is imported. Everything else (SUPABASE_SERVICE_ROLE_KEY, ENCRYPTION_KEY, GMAIL_*, Pathao/Meta secrets) is read lazily inside request handlers, so it's supplied at container runtime — changing those just needs a restart, not a rebuild.

Practical consequence: moving environments means rebuilding the app image (Kong URL and keys differ), but db/auth/rest/storage need no rebuild at all.

Server-side code has to prefer the internal URL — and that has a sharp edge

Server-only code (server components, middleware, route handlers, supabaseAdmin) reaches Kong over the Docker network at SUPABASE_INTERNAL_URL (http://kong:8000) rather than the browser-facing NEXT_PUBLIC_SUPABASE_URL, since the two are only reachable from different network contexts in a containerized deployment. See Bugs found & fixed for the real incident this caused with session cookies — anyone adding a new server-side Supabase client must reuse the shared, explicit cookie name, not rely on the library's default derivation.

Database schema

supabase/migrations/ holds 36 tracked migration files, but does not reconstruct the schema from an empty Postgres by itself. A handful of core tables (like store_settings) were created through a one-time manual project migration before this repo's migration history started being tracked, and only live in schema.sql — a full schema snapshot. The bootstrap script (docker/scripts/apply-migrations.sh) always runs both, in order:

  1. Load schema.sql — brings in everything the tracked migrations alone would miss.
  2. Replay every migration in supabase/migrations on top. All are written defensively (IF NOT EXISTS/IF EXISTS), so anything already in the snapshot no-ops, and anything added after the snapshot date applies for real.

This is a one-time step per fresh database — not something that runs on every deploy.

Running it locally

There are three distinct ways to run the app locally, for three different purposes. They share one docker-compose.yml; overlays and env files select which one you get.

dev

docker-compose.yml + docker-compose.dev.yml, docker/.env. Adds local MinIO standing in for R2. Day-to-day feature work.

prod (rehearsal)

docker-compose.yml alone, docker/.env.prod. Real R2 bucket, stricter auth defaults, optionally a full copy of real production data. A dress rehearsal of the exact stack the VPS runs.

local-vps-backend new

docker-compose.yml + docker-compose.local-vps-backend.yml. Runs only the app container — no local Postgres/Auth/Kong at all — pointed straight at the live VPS's Kong. One database, nothing to keep in sync.

Why local-vps-backend exists

The "prod rehearsal" mode keeps its own full copy of the database, which drifts from the live VPS the moment either one changes — every drift incident in this project's history came from exactly that gap. Pointing the local app straight at the VPS's public API removes the second database entirely: reads are always current, and there's nothing to resync. It talks to real production data, so writes (creating orders, editing customers, connecting Pathao) happen for real — treat it accordingly.

First-time setup — dev

  1. cp docker/.env.example docker/.env
  2. ./docker/scripts/generate-keys-for.sh docker/.env — generates JWT secret, ANON/SERVICE_ROLE keys, Postgres password, etc. Fill in app-specific values (GMAIL_*, UPSTASH_*, ENCRYPTION_KEY) yourself.
  3. ./docker/scripts/bootstrap.sh dev — required on first boot: GoTrue and Storage-API create their own Postgres schemas on startup, and this project's migrations reference auth.users/auth.uid(), so bring-up order matters (db → auth/storage/rest/minio → schema/migrations → storage buckets → kong/studio/meta/app).

First-time setup — prod rehearsal

  1. Create a Cloudflare R2 bucket + API token (Access Key ID + Secret) if you don't have one.
  2. cp docker/.env.prod.example docker/.env.prod, then ./docker/scripts/generate-keys-for.sh docker/.env.prod. Fill in the R2 section and app-specific values. Every secret here must differ from dev's — never reuse.
  3. ./docker/scripts/bootstrap.sh prod — same ordering as dev, minus the MinIO step.
  4. Optional, once: pull real Cloud data in via docker/scripts/migrate-data/ — see the migration pipeline.

First-time setup — local-vps-backend

  1. cp docker/.env.local-vps-backend.example docker/.env.local-vps-backend.
  2. Fill in SUPABASE_PUBLIC_URL, ANON_KEY, SERVICE_ROLE_KEY, and ENCRYPTION_KEY with the VPS's real, current values (see docker/SERVICE_CREDENTIALS.md, or fetch them directly from the VPS's own docker/.env.prod). A mismatched ENCRYPTION_KEY doesn't error loudly — it just silently fails to decrypt real stored credentials.
  3. pnpm docker:local-vps:build.
Compose merge gotcha

depends_on is merged across compose files, not replaced — an override file can't simply clear a base file's depends_on: kong: condition: service_healthy by setting an empty list. That's why the docker:local-vps:* scripts pass --no-deps explicitly, rather than relying on the override alone. If you ever swap env files mid-session for the base stack's other services (kong, studio, etc.) without also using --no-deps/targeting them precisely, they'll recompute their config against whatever env file you passed and may get recreated with the wrong values — always bring the base stack back up with its own real env file (docker/.env.prod) afterward if that happens.

Verifying it actually works

  • Sign in through the real login flow at localhost:3000 — confirms GoTrue is reachable through Kong.
  • Load a public storefront page — confirms PostgREST + RLS against the migrated schema.
  • Open Studio through Kong (basic-auth) and browse the Table Editor — confirms meta is wired.
  • Upload a store logo/product image and confirm the returned URL loads — then check it landed in MinIO's console (dev) or the R2 bucket dashboard (prod).

Not testable until a real domain exists: live Pathao webhook delivery (needs a public HTTPS URL), TLS.

Deployment — GitHub Actions

.github/workflows/deploy.yml runs on every push to main (or manually via workflow_dispatch). It deliberately does a small, safe set of things — and just as deliberately doesn't do several others.

What this workflow never does

It never touches the database, runs migrations, or regenerates most of docker/.env.prod. Real secrets — ENCRYPTION_KEY, R2 credentials, JWT_SECRET, POSTGRES_PASSWORD — live only in docker/.env.prod on the VPS itself and are never seen by CI. Those stay manual, deliberate steps (see Migrating to a new VPS) — exactly the kind of thing that shouldn't happen unattended on every push.

  1. Checkout the pushed commit.
  2. Set up SSH using the VPS_SSH_KEY secret.
  3. Ensure swap exists — idempotent 2 GB swapfile creation, a safety net since next build can spike memory on a small VPS.
  4. Sync the repo to the VPS via rsync, excluding node_modules, .next, .git, the Postgres data directories, and every real env file.
  5. Patch domain/URL settings in the VPS's existing docker/.env.prod — SITE_URL, SUPABASE_PUBLIC_URL, API_EXTERNAL_URL, ADMIN_API_URL, SITE_DOMAIN, API_DOMAIN — derived from secrets and applied with sed, values substituted on the runner before the command is sent over SSH (so no remote-side escaping is needed).
  6. Open 80/443 in ufw, only when the USE_PROXY repo variable is "true".
  7. Reconcile the stack and rebuild app — docker compose up -d, then up -d --build app specifically, so the new code's build-time env values actually take effect. Includes the Caddy overlay only when USE_PROXY is on.
  8. Verify — talks to Caddy directly by IP + SNI override (--resolve) rather than the public hostname, so the check is accurate even before DNS is cut over; a genuinely open endpoint (/auth/v1/.well-known/jwks.json, not /auth/v1/health, which requires an API key) proves Kong/GoTrue are actually serving. A best-effort, non-fatal check against the real public URL reports once DNS is live too.

Changing the domain later is just updating the SITE_URL/SUPABASE_PUBLIC_URL secrets (and flipping USE_PROXY to "true" once DNS + Caddy are ready), then pushing or re-running the workflow.

Cloud → self-hosted data migration

docker/scripts/migrate-data/ is one-time tooling to pull the live Supabase Cloud project's real data — auth users, every public-schema table, storage files — into a self-hosted stack. Not part of regular dev/prod bring-up; run once against a freshly-bootstrapped target (or re-run in full to re-sync, see the callout below).

Three secrets, never stored in this repo

OLD_URL (source project's API URL), OLD_KEY (source service_role key), and SOURCE_DB_URL — a direct Postgres connection string from Supabase's dashboard. Use the session pooler connection string, not the direct one: Supabase's direct-connection hostname is IPv6-only unless the project has the IPv4 add-on, and most local/CI networks can't reach it.

Order (matters)

  1. migrate-auth.mjs — recreates every user in the target via the GoTrue Admin API. Passwords can't be carried over (not exposed by any API); users get a random password and use "Forgot Password". Builds auth-id-mapping.json (old id → new id) — idempotent, skips users already mapped on re-run.
  2. migrate-public-data.sh — pg_dump --data-only --schema=public from the source, pg_restore into the target, run inside the shei-hoise-db container. Copies every table's rows as-is, still referencing the old auth ids and old storage hostname.
  3. fix-image-urls.sh — rewrites the source project's hostname to the target's storage hostname across every stored image/avatar URL. Storage-API keeps the same URL shape regardless of backend, so this is a pure hostname swap.
  4. fix-auth-id-references.mjs — walks the id mapping and updates every foreign key that references the old auth ids (store_customers.auth_user_id, store_subscriptions.user_id, subscription_invoices.user_id).
  5. migrate-storage.mjs — copies every bucket's files from source to target, upsert: true.
One more step this list misses

public.users is a companion/profile table keyed 1:1 with auth.users by id. Since GoTrue assigns brand-new ids and the data-only restore copies public.users rows with their old ids, the two drift apart the moment steps 1–2 finish — breaking every "which store does this logged-in user own" check. fix-public-users-ids.sh (not part of the original five-script list, added after finding this bug) adds ON UPDATE CASCADE to all 13 foreign keys pointing at public.users(id), then remaps every id — run it right after step 4.

Running it

OLD_URL='https://<source-ref>.supabase.co' \
OLD_KEY='<source service_role key>' \
SOURCE_DB_URL='postgresql://postgres.<ref>:<password>@<pooler-host>:5432/postgres' \
docker/scripts/migrate-data/run-all.sh prod

Or run each script individually (necessary if you also need the public.users fix, or want to inspect between steps).

Re-syncing later (closing drift)

Cloud stays a live, moving target for as long as anything still writes to it. To pull a fresh, complete copy rather than a delta: TRUNCATE every public-schema table (respecting CASCADE), then re-run the full pipeline above in order. All five scripts (plus the public.users fix) are safe to re-run against a freshly truncated target.

Real incident — wait for storage to fully finish

migrate-storage.mjs re-uploads every file on every run (no skip-if-unchanged logic) and can take well over ten minutes for a thousand-file bucket. If the database dump is taken before that finishes, files re-uploaded afterward get a new internal storage.objects.version that the already-taken dump doesn't know about — the restored target then points at a version id that's been superseded, and Storage-API returns 404/400 for those files even though the metadata row exists. Always let storage migration finish completely before dumping the database for a restore.

Real incident — the customer list breaks above a URL-length threshold

An unrelated app bug, found while investigating a "data is missing" report during migration testing: getAllStoreCustomers used to fetch every linked customer id, then pass the entire list to a single .in(customerIds) filter. For a store with ~900 customers that built a 33 KB+ URL, which Kong rejects outright with 414 URI too long — the customer list came back empty for any sufficiently active store, on any backend, including the original Vercel deployment. Fixed by querying from store_customer_links scoped by store_id directly, embedding the related store_customers row through the foreign key instead of ever building a giant id list. Worth remembering as a pattern to avoid elsewhere: never build an .in() filter from an unbounded, previously-fetched id list — embed through the relationship instead.

Migrating to a new VPS

This is the condensed, battle-tested version of docker/VPS_DEPLOYMENT.md — the exact sequence that's actually been run successfully, including everything that went wrong the first few times.

0. Prerequisites

  • A real domain, with access to add DNS records.
  • A working local "prod" rehearsal — confirm with docker compose -f docker/docker-compose.yml --env-file docker/.env.prod ps showing everything healthy.

1. Provision the VPS

  • 2 vCPU / 4 GB is enough for this workload (a small B-series/CPX-class instance).
  • SSH key auth only; disable password auth.
  • ufw allow 22 && ufw allow 80 && ufw allow 443 && ufw enable.
  • Install Docker Engine + the Compose plugin.
If the VPS is on a cloud provider with its own network firewall (Azure NSG, AWS security groups, GCP firewall rules) — this is not optional

ufw is not the only firewall in the path. A cloud-level network security group sits in front of the VM entirely separately, and a port can be open in ufw while still being silently dropped upstream — the connection just hangs (no refusal, no error), which is the exact signature to watch for. This bit twice in one deployment: once for SSH itself after a reboot, once for ports 80/443 during the domain cutover. Both times the actual cause was rule priority ordering — a lower-priority-number "Deny" rule silently overrode a newly added "Allow" rule. When adding a port, always: (1) add it to ufw, (2) add the matching rule in the cloud provider's own NSG/security-group console, and (3) give that rule a priority/order number lower than any blanket deny.

2. DNS

Two records, both pointed at the VPS's IP — the browser calls Kong directly (NEXT_PUBLIC_SUPABASE_URL), not just the app, so both need their own public hostname:

RecordPoints to
sheihoise.com (A)the app, via Caddy
api.sheihoise.com (A)Kong, via Caddy

Let DNS propagate before bringing up Caddy — Let's Encrypt issuance fails if the domain doesn't resolve to the VPS yet. If a root/apex domain was previously hosted elsewhere (e.g. Vercel), double-check the exact A record actually changed — some registrars keep a separate ALIAS/ANAME record for the apex that silently overrides a new plain A record, and editing in place can fail; delete the old record and add a fresh one instead.

3. Copy the repo, build docker/.env.prod

Regenerate freshCopy byte-for-byte, never regenerate
JWT_SECRET, POSTGRES_PASSWORD, ANON_KEY, SERVICE_ROLE_KEY, DASHBOARD_PASSWORD ENCRYPTION_KEY (+version), R2 credentials (GLOBAL_S3_*, AWS_ACCESS_KEY_ID/SECRET)

ENCRYPTION_KEY decrypts values already stored in the database being cloned — a fresh key silently breaks decryption for every store's saved credentials. R2 values must stay identical because the restored database's image URLs already point at that exact bucket.

New real values: SITE_URL, SUPABASE_PUBLIC_URL, API_EXTERNAL_URL, SITE_DOMAIN, API_DOMAIN, a fresh POSTGRES_DATA_DIR. Don't publish Postgres's port at all on the VPS — use an SSH tunnel for ad-hoc access.

4. Clone the database — a direct dump/restore, not a re-migration

Since the local prod rehearsal already has every fix applied, the fastest, most reliable path is cloning its Postgres directly rather than re-running the Cloud migration scripts against the new VPS.

  1. docker/scripts/migrate-data/dump-local-prod-db.sh — full, all-schema dump (not just public) of the working local prod database.
  2. scp the dump to the VPS.
  3. Stop the whole stack, wipe docker/volumes/db/data completely, bring up only db fresh.
  4. Restore: 
    docker exec shei-hoise-db pg_restore \
  -U supabase_admin -d postgres \
  --clean --if-exists --single-transaction \
  full-prod.dump
    Must be supabase_admin, not postgres

    Despite the name, postgres is a restricted role on this image — it mirrors Supabase Cloud's own role model, and lacks the privileges to touch event triggers or other full-cluster objects. --clean --if-exists is required even against a freshly emptied data directory, since the base image's own bootstrap already creates some schema objects that need cleaning before the restore's copies land.

  5. Bring up auth, rest, storage — expect "migrations already up to date, nothing to apply" in the auth logs, confirming a clean restore against matching versions, not a fresh self-migration.
  6. Bring up studio, meta, kong, then app (rebuild, for the new domain's build args), then caddy once DNS has propagated.

5. Image URLs need rewriting — potentially twice

Stored image URLs carry whatever hostname was active when the data was migrated. Moving hosts means running the same old_host → new_host rewrite pattern again (across product_images.image_url, stores.logo_url/banner_url, categories.image_url, customer_profiles.avatar_url, user_profiles.avatar_url) — first from the local rehearsal's hostname to the VPS's IP (so the site works immediately while DNS propagates), then again from the IP to the final real domain once DNS and TLS are confirmed working. Storage-API keeps the same URL shape regardless of backend, so it's always a pure hostname swap.

6. Caddy & TLS

Two site blocks, since the browser calls Kong directly and not just the app:

{$SITE_DOMAIN} {
	reverse_proxy app:3000
}
{$API_DOMAIN} {
	reverse_proxy kong:8000
}
Caddy's staging-CA fallback is a feature, not a bug

If Caddy repeatedly fails to obtain a certificate against the real Let's Encrypt endpoint (DNS not ready yet, port 80/443 blocked upstream), it automatically falls back to Let's Encrypt's staging CA — which issues untrusted certificates, but has far more forgiving rate limits — so it can keep retrying without burning through the real, limited quota. Once the real blocker (DNS, firewall) is fixed and a challenge actually succeeds, it switches back to the production CA automatically on its next retry. Restarting the caddy container forces an immediate retry instead of waiting for its backoff timer.

  • GoTrue's ADDITIONAL_REDIRECT_URLS and the password-reset system's site URL now point at the real domain automatically, from docker/.env.prod — no separate dashboard config needed.
  • Re-register the Pathao webhook URL if it was previously registered against a different host.
  • Add the GitHub Actions secrets (see Required GitHub configuration) so future deploys work without manual SSH.

Verification checklist

  1. docker compose ... ps — everything healthy.
  2. curl -I https://api.<domain>/auth/v1/.well-known/jwks.json and curl -I https://<domain>/ — valid certs, 200s.
  3. Sign in as a real migrated store owner — the single most important check, since this is exactly the class of bug (public.users id sync) found and fixed during the original migration.
  4. Load a real storefront page, confirm product images render straight from R2.
  5. Request a password reset through the real UI end to end, confirm the emailed link uses the real domain.
  6. Confirm the Pathao webhook endpoint is genuinely reachable now that a public HTTPS URL exists.
  7. Diff row counts for the core tables (orders, store_customers, products, stores, store_subscriptions) against whatever was live immediately before cutover, to catch any last-minute drift.

Bugs found & fixed — read before touching auth or list queries

Session cookie name mismatch (auth silently appeared broken everywhere)

@supabase/ssr auto-derives its session cookie name from whichever Supabase URL it's given, unless told otherwise. The browser client uses NEXT_PUBLIC_SUPABASE_URL (the public domain); several server-side clients prefer SUPABASE_INTERNAL_URL (http://kong:8000) for reachability inside Docker. Two different URLs auto-derive two different cookie names — the server was reading a session cookie that literally didn't exist under the name it was looking for, so every server-rendered auth check (subscription status, and anything else server-side) always looked logged out, regardless of whether the user actually was.

Fix: every client construction site (src/lib/supabase/client.ts, server.ts, middleware.ts, src/app/auth/callback/route.ts) now passes an explicit, identical cookieOptions: {'{'} name: "sb-shei-hoise-auth-token" {'}'}, decoupling the cookie name entirely from which URL each one happens to talk to.

Rule going forward

Any new place that constructs a Supabase client with createBrowserClient or createServerClient must pass the same explicit cookieOptions.name. Never let it fall back to the library's default derivation.

Customer list 414 "URI too long" for active stores

See the migration pipeline section above — same bug, same fix, kept there since it was found while investigating a migration-adjacent report.
